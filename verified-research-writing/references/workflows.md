# Choose the right writing workflow

Use only the route that matches the user's request. Do not turn every assignment into a systematic review or imply work the user did not perform.

## Course paper or research manuscript

1. Extract the assignment/rubric or journal requirements: purpose, audience, scope, required sections, length, citation style, tables/figures, and disclosures.
2. Confirm the research question and the intended kind of contribution. Distinguish a proposed argument from an empirically demonstrated result.
3. Find and verify literature, build an evidence ledger, then draft the requested sections.
4. Check every factual claim and quantitative statement against the evidence ledger and supplied data.
5. Run the submission checklist in `submission-checks.md`.

## Experimental or lab report

1. Collect the actual protocol, notebook, raw data, assignment rubric, and any instrument/calibration details the user has.
2. Build a data dictionary: variable, unit, sample/group, measured or derived status, and missing values.
3. Check data integrity and perform only analyses supported by the design and supplied data. Keep calculations reproducible.
4. Draft methods from the protocol and results from the actual observations. Never reconstruct missing apparatus, measurements, calibration, or approvals.
5. Use the evidence ledger for literature cited in the introduction/discussion; do not use literature findings as the user's experimental results.
6. Check the report against the rubric and the data-to-text consistency list in `evidence-and-data.md` and `submission-checks.md`.

## Narrative literature review

1. Agree on scope, date range, language, and key concepts.
2. Search suitable sources and keep a compact log of actual databases, queries, and dates.
3. Build the evidence ledger and organize studies by question/theme, including null or conflicting findings.
4. Synthesize the evidence and its limitations. Do not claim exhaustive coverage, formal screening, or systematic methods unless those steps were performed and documented.

## Systematic review

Only use this route when the user asks for a systematic review or has a real systematic-review protocol. If the work is already underway, document what was actually done; never retroactively invent protocol registration, independent reviewers, screening decisions, or counts.

1. Before screening, define the question and eligibility criteria. Use a question framework appropriate to the field (for example, PICO/PICOS for intervention questions or another suitable framework).
2. Record the protocol/version and registration status truthfully. No registration is preferable to a fabricated registration.
3. Search multiple appropriate databases. Save each exact search string, platform, coverage/filters, date/time, and result count. Translate syntax per database; do not report one database's query as if it were used everywhere.
4. Export records, deduplicate with a documented method, and track title/abstract and full-text decisions separately. Keep a reason for each full-text exclusion. If AI assists screening, label it as assistance and require the human reviewers the protocol calls for to make/confirm decisions.
5. Extract study characteristics and outcomes into the evidence ledger. Use design-appropriate critical-appraisal tools only when appropriate; do not invent quality scores.
6. Synthesize only comparable evidence. Do not pool incompatible outcomes or infer statistical significance from narrative summaries. State when meta-analysis was not conducted and why.
7. Report actual flow counts from the screening log. Use the reporting guideline required by the journal/field; PRISMA 2020 is a reporting guideline for systematic reviews, and PRISMA-S provides additional search-reporting items. A checklist does not itself make the methods systematic.

If the question, eligibility criteria, searches, or screening records are missing, do not write completed review results or a populated PRISMA flow diagram. Offer to draft a protocol and a blank screening/search log, and state which records are needed to continue. Any illustrative flow diagram must remain clearly blank or labeled hypothetical and must not be presented as this review's findings.

At minimum, use these log fields:

| Search log | Screening log |
|---|---|
| Database/platform | Record ID |
| Exact query and syntax | Citation/DOI |
| Date/time searched | Screening stage (title/abstract or full text) |
| Coverage, filters, and language limits | Decision (include/exclude/uncertain) |
| Records returned and export filename | Exclusion reason at full-text stage |
| Searcher and notes on errors/changes | Reviewer and decision date |

Keep screening counts derivable from the record-level log. If only aggregate numbers are available, report that limitation and do not fabricate record-level reasons.

## Scoping review

Map the breadth, concepts, and evidence types within an explicit scope. Record protocol, eligibility, search sources/strategies, selection, charting methods, and counts. Use PRISMA-ScR when appropriate for reporting; do not automatically apply intervention-specific risk-of-bias procedures to a scoping review.

## Reporting-guideline selection

Follow the journal's required guideline first. Otherwise identify the study/review design and select the matching current guideline from a reputable reporting-guideline library. Do not claim compliance until each applicable item has been checked against the manuscript.

Reference pages:

- [PRISMA 2020](https://www.prisma-statement.org/prisma-2020)
- [PRISMA-S search reporting](https://www.prisma-statement.org/prisma-search)
- [PRISMA-ScR](https://www.prisma-statement.org/scoping)
